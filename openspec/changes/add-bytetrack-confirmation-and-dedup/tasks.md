## 1. Track confirmation delay

- [ ] 1.1 Add `ConsecutiveMatches` (int) to the private `Track` class in `src/NBA.Tracking/ByteTrackPlayerTracker.cs`, set to `1` when a track is spawned (design.md: a spawn counts as its own first match) and incremented on every successful match in `ApplyMatch`. Add `minimumConsecutiveFrames` (default `3`) as a new constructor parameter. Add an `IsConfirmed` computed check (`ConsecutiveMatches >= minimumConsecutiveFrames`). Verify the solution builds.
- [ ] 1.2 In the aging step of `Update` (where `LostFrames` is currently incremented for unmatched tracks), discard any track that is unmatched this attempt and not yet confirmed (`!IsConfirmed`) immediately — remove it from `_tracks` outright instead of incrementing its `LostFrames` toward `maxLostFrames`. Confirmed tracks keep today's existing aging behavior unchanged. Verify with a unit test: a spawned track that misses the very next `Update` call is absent from `_tracks` afterward (assert via subsequent behavior, e.g. it is never returned even if a later detection reappears at the same position with a new ID).
- [ ] 1.3 Update `ToVisiblePlayers` to require `IsConfirmed` in addition to the existing `LostFrames <= maxVisibleLostFrames` filter. Verify with a unit test: a freshly spawned track (before reaching `minimumConsecutiveFrames`) is not present in `Update`'s or `PredictOnly`'s returned list even though it exists internally and is eligible to be matched against.
- [ ] 1.4 Add unit tests in `tests/NBA.Tracking.Tests/ByteTrackPlayerTrackerTests.cs` covering the spec's confirmation scenarios: a candidate matching every attempt through `minimumConsecutiveFrames` becomes visible with a stable ID from that point on; a candidate that breaks its streak before confirmation is discarded and never appears; `minimumConsecutiveFrames = 1` reproduces today's immediate-visibility behavior exactly.
- [ ] 1.5 Update the existing test "an unmatched high-confidence detection creates a new track with a fresh ID" (from `add-bytetrack-tracking`) to account for the new default: either drive it through `minimumConsecutiveFrames` consecutive matching `Update` calls before asserting the ID appears, or construct the tracker in that test with `minimumConsecutiveFrames: 1` if the test's intent is specifically about round-1-spawn behavior in isolation. Verify the full existing suite still passes.

## 2. Duplicate-track suppression

- [ ] 2.1 Add a `duplicateIouThreshold` (default `0.95`) constructor parameter. After association rounds and new-track spawning complete in `Update` (before the existing aging step, so a duplicate isn't also separately aged this same call), add a pass that computes IoU over every pair of live tracks' `LastBox` and, for each pair at or above `duplicateIouThreshold`, marks the loser for removal per the tie-break in 2.2. Verify the solution builds.
- [ ] 2.2 Implement the tie-break exactly as design.md specifies: keep the track with the higher `ConsecutiveMatches`; on an exact tie, keep the lower `Id`. Remove the loser from `_tracks` immediately (its ID is never reused, consistent with the existing termination path). Verify with a unit test using hand-built boxes: two tracks with overlapping `LastBox` above threshold and differing `ConsecutiveMatches` — the shorter-history one is removed and absent from subsequent `Update` results.
- [ ] 2.3 Add a unit test for the tie-break itself: two same-attempt spawns (equal `ConsecutiveMatches`) with overlapping boxes above threshold — assert the lower-ID track survives and the higher-ID one is removed, deterministically across repeated runs.
- [ ] 2.4 Add a unit test for the "unconfirmed candidate duplicates an established track" scenario: a confirmed track and a same-attempt newly spawned candidate whose boxes overlap above threshold — assert the candidate is discarded (never reaches confirmation) and the established track is unaffected.
- [ ] 2.5 Add a unit test confirming tracks with ordinary spacing (IoU below `duplicateIouThreshold`) are never affected by this pass, using the existing crossing-players fixtures from `add-team-color-track-gating`'s tests as a baseline (both tracks survive; team-color veto behavior from that change is unchanged).
