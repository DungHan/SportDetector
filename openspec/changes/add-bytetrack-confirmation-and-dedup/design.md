## Context

`ByteTrackPlayerTracker` (`src/NBA.Tracking/ByteTrackPlayerTracker.cs`) already runs, per `Update` call: motion prediction for every live track (`BoxMotionPredictor`, four decoupled per-axis Kalman filters), a two-round IoU association (high-confidence detections first, then low-confidence detections against tracks still unmatched after round one), new-track spawning from round-one leftovers, lost-frame aging, and a team-color veto folded into both rounds' `isEligible` check (`add-team-color-track-gating`). This was all built as a deliberate, documented divergence from the reference ByteTrack implementation (the `supervision` Python library, as used by `roboflow/sports`): `add-bytetrack-tracking/design.md` records the choice of **greedy IoU matching over the Hungarian/optimal-assignment algorithm** the reference implementation uses (cost matrix = `1 - IoU`, solved via `linear_sum_assignment` there; sorted-and-claimed greedily here, same pattern as `OnnxPlayerDetector.SuppressOverlapping`'s NMS), and **four independent 1D Kalman filters over `cx, cy, w, h`** instead of the reference's one coupled 8D filter — both trade a small amount of optimality for avoiding a new dependency, justified by this domain's small per-frame player count.

Studying that reference implementation further (to understand how it stays stable when detections are spurious or duplicated) surfaced two mechanisms this project's tracker doesn't have, both implemented in `supervision`'s `ByteTrack.update_with_tensors`:

- `minimum_consecutive_frames`: a spawned track only becomes `is_activated` (and is only included in `output_stracks`, the list returned to the caller) once it has matched for that many consecutive frames from its spawn. Below that, a single spurious detection can spawn a track internally but it's never surfaced.
- `remove_duplicate_tracks`: after each frame's association, every pair of tracked/lost tracks is compared by `iou_distance` (`1 - IoU`); pairs under `0.05` (i.e. IoU ≥ 0.95, near-total overlap) are deduplicated, keeping whichever track has the longer running duration (`frame_id - start_frame`) and discarding the other.

This design ports both, adapted to this project's existing greedy-matching, frame-stepped (not wall-clock), constructor-parameter-driven style rather than copying the reference's data structures.

Two existing pieces of this class's state matter for both new mechanisms and are addressed explicitly below: the `maxVisibleLostFrames` grace window (a track coasting purely on motion prediction past that many misses is withheld from `ToVisiblePlayers` but stays alive internally until `maxLostFrames`) and the per-track color EMA seeded at spawn (`add-team-color-track-gating`).

## Goals / Non-Goals

**Goals:**
- A newly spawned track must survive a configured number of consecutive matched detection attempts before it is ever surfaced to a caller or exposes a track ID.
- A post-association pass removes near-total-overlap duplicate tracks every detection attempt, keeping the one with the longer matched history.
- Both new behaviors compose with the existing two-round matching, occlusion buffer, `maxVisibleLostFrames` grace window, and team-color veto without changing any of their existing semantics for already-confirmed tracks.

**Non-Goals:**
- Re-litigating greedy-vs-Hungarian matching or the decoupled-Kalman-filter decision — both stand as-is (see Context).
- Tuning `minimumConsecutiveFrames` / `duplicateIouThreshold` against real broadcast footage — defaults are chosen to mirror the reference implementation's own defaults, exposed as constructor parameters so they can be retuned without a code change, same posture every other threshold on this class already takes.
- Retroactively archiving the three completed-but-unarchived `tracking/player-tracking` changes this design's spec delta builds on (`add-bytetrack-tracking`, `add-team-color-track-gating`, `throttle-player-detection-cadence`) — out of scope for this change.

## Decisions

**Confirmation is tracked as a per-`Track` consecutive-match counter, not a separate candidate list.** Add a `ConsecutiveMatches` field to the private `Track` class, incremented on every successful match (round 1 or round 2) and reset to `0`... actually **not reset** on a miss — a miss during the confirmation window instead discards the candidate immediately (see next decision) rather than resetting a counter that would otherwise let it retry indefinitely. `IsConfirmed => ConsecutiveMatches >= minimumConsecutiveFrames`. `ToVisiblePlayers` (and any future caller-facing list) filters on `IsConfirmed` in addition to the existing `LostFrames <= maxVisibleLostFrames` check. This reuses the existing single `_tracks` list and `ApplyMatch` path rather than introducing a parallel "candidates" collection, keeping the one-list invariant the class already relies on (e.g. for `GreedyIouMatcher` inputs, which must include unconfirmed candidates so they can still be matched against and eventually confirmed or discarded).

**An unconfirmed candidate that misses a detection attempt is discarded immediately, not aged through `maxLostFrames`.** Upstream ByteTrack's unconfirmed tracks live in the same `tracked_stracks` pool and can in principle persist across the normal lost-track lifecycle before ever activating, but this project's simpler greedy/single-list design makes "discard on first miss" both simpler and a better match for the stated intent (a spurious detection shouldn't get a multi-frame occlusion grace period it never earned by being confirmed first). Concretely: in the aging step, a track with `!IsConfirmed && LostFrames > 0` (i.e. it just missed this attempt, at any point before confirmation) is removed outright instead of having `LostFrames` incremented toward `maxLostFrames`. This also sidesteps a question that doesn't otherwise arise: an unconfirmed track can never reach `PredictOnly`'s motion-prediction-without-detection path, since it's discarded before it would ever coast.

**Default `minimumConsecutiveFrames = 3`**, matching `supervision.ByteTrack`'s own default, and the value `sports`' own example code passes (`sv.ByteTrack(minimum_consecutive_frames=3)`). `minimumConsecutiveFrames = 1` reproduces today's behavior exactly (a track confirms on its spawning match, i.e. immediately) — a useful escape hatch, not a special-cased mode.

**Duplicate suppression runs once per `Update` call, after both association rounds and new-track spawning, comparing every live-track pair (confirmed and unconfirmed) by IoU of `LastBox`.** Using `LastBox` (this attempt's reported box — matched detection box, or motion-predicted box while coasting) rather than `PredictedBox` catches the case the proposal calls out directly: a freshly matched/spawned track's real detection box overlapping a separately coasting track's stale prediction. Threshold is expressed as `duplicateIouThreshold` (IoU, default `0.95`) rather than the reference's `iou_distance < 0.05` — same value, framed consistently with this class's other thresholds which are all IoU (higher = more overlap required), not distance.

**Tie-break: keep the track with more `ConsecutiveMatches`; on an exact tie, keep the lower track ID.** Track ID is monotonically assigned at spawn (`_nextTrackId++`), so "lower ID" is equivalent to "spawned earlier" without needing a separate spawn-order timestamp — mirrors the reference implementation's `frame_id - start_frame` duration comparison (longer-lived wins) using data this class already has, while adding a fully deterministic tie-break the reference implementation doesn't need (it compares real frame counts, which are unlikely to tie; this class's greedy matching could plausibly produce two same-attempt spawns).

**Duplicate suppression naturally resolves the "unconfirmed candidate duplicates an already-established track" case without special-casing it**: an established confirmed track always has `ConsecutiveMatches >= minimumConsecutiveFrames`, strictly greater than a same-attempt spawn's `1`, so the confirmed track always wins the history comparison and the candidate is discarded — consistent with never letting it reach confirmation. No separate code path is needed for "candidate vs. confirmed" versus "confirmed vs. confirmed" duplicates; one comparison covers both, which is why the spec (this change's `specs/tracking/player-tracking/spec.md`) states both as scenarios of the same requirement rather than two requirements.

**Interaction with the color EMA (`add-team-color-track-gating`): unchanged.** A candidate still seeds its color estimate from its spawning detection and updates it via EMA on every match, confirmed or not — discarding an unconfirmed candidate before confirmation simply throws away that in-progress estimate along with the rest of the track state, no different from how a confirmed track's color state is discarded on normal termination today. No design change needed here; noted to close out the proposal's explicit question.

**Interaction with `maxVisibleLostFrames`: additive, independent gate.** `ToVisiblePlayers` becomes `_tracks.Where(t => t.IsConfirmed && t.LostFrames <= maxVisibleLostFrames)`. A track must be both confirmed and not coasting-too-long to be visible; the two gates don't otherwise interact (a track cannot be unconfirmed and also past `maxVisibleLostFrames`, since unconfirmed tracks are discarded on their first miss, well before `maxVisibleLostFrames` could apply — but the `&&` is written explicitly rather than relying on that invariant, so the visibility rule stays correct on its own terms if the discard-on-first-miss decision above is ever revisited).

**Existing `ByteTrackPlayerTrackerTests` case affected: "an unmatched high-confidence detection creates a new track with a fresh ID"** (from `add-bytetrack-tracking`'s task 4.2) asserted the new ID appears in the very next `Update`'s return value. With `minimumConsecutiveFrames`'s default of `3`, that assertion becomes true only after two further consecutive matching `Update` calls. This is an intentional behavior change flagged explicitly here since it touches a previously-passing test's assertion, not a regression to fix around — `tasks.md` includes updating that test alongside adding new confirmation-specific coverage.

## Risks / Trade-offs

- [Discard-on-first-miss for unconfirmed candidates, rather than reusing `maxLostFrames`] → a real player whose very first detection happens to be followed by one genuinely missed frame (e.g. entering from off-screen into partial occlusion) loses that track and gets a new ID once redetected, instead of surviving via the occlusion buffer. Accepted: the occlusion buffer's purpose is to protect *established* identity through brief gaps, not to give every brand-new candidate the same grace before it's proven real; `minimumConsecutiveFrames` is a constructor parameter and can be lowered if this is observed to cost real tracks in practice.
- [`minimumConsecutiveFrames > 1` delays every real player's first appearance by that many attempts, not just spurious ones] → same trade-off the reference implementation accepts; a few attempts of latency before a genuine new player gets a visible box is preferable to every misfire getting a permanent, never-reused ID slot and a flickering box.
- [Comparing every live-track pair for duplicates is O(n²) per `Update` call] → per-frame player counts in this domain are small (a couple dozen at most), same justification already accepted for greedy O(n²)-ish matching; revisit only if profiling ever shows otherwise.
- [Duplicate suppression could, in principle, discard the "wrong" track if a longer-lived track has actually drifted (bad motion prediction) onto a different player than a freshly-spawned correct detection] → mitigated by using `LastBox` (real detection box when matched this attempt) rather than `PredictedBox` for the freshly-matched side of the comparison, and by the existing team-color veto already having had a chance to prevent the wrong association from producing this situation in the first place; not eliminated, but consistent with the reference implementation's own duration-based tie-break, which has the same theoretical failure mode.
