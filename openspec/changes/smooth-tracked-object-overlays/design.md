## Context

`src/NBA.Tracking/BoxMotionPredictor.cs` already runs four independent `Axis1DKalmanFilter`s (center-x, center-y, width, height) per player track. `Axis1DKalmanFilter.Correct(measurement)` computes the textbook Kalman posterior (`_position += k0 * innovation`) - a principled, noise-aware blend of the prior predicted state and the new measurement - but only `_position` (private) is updated; nothing currently reads it back out except via another `Predict()` call, which would advance the state an extra step rather than just report the already-blended estimate. `ByteTrackPlayerTracker.ApplyMatch` (`src/NBA.Tracking/ByteTrackPlayerTracker.cs:258-266`) calls `track.Predictor.Correct(box)` for its side effect only and then overwrites `track.LastBox` with the raw detection box, discarding the very estimate the filter just computed.

The ball has no analogous filter at all today: `MainWindowViewModel` picks the current frame's highest-confidence raw `Ball` detection directly for both the raw-view box and the minimap marker (`src/NBA.App/ViewModels/MainWindowViewModel.cs:909-918` and the `otherAnnotations` construction), with no persistence across frames.

See proposal.md for the motivation (visible jitter/drift on both).

## Goals / Non-Goals

**Goals:**
- Report an already-filtered position estimate instead of a raw per-frame detection box, for both players and the ball, reusing the existing Kalman machinery rather than adding a second, separate smoothing layer.
- Give the ball the same "coast through a brief miss, don't just vanish" behavior players already get from the occlusion buffer, scaled down to a single object with no identity to protect.

**Non-Goals:**
- No change to association logic, confirmation/dedup, or team-color gating in `ByteTrackPlayerTracker` - only which box value a confirmed/coasting track reports.
- No multi-ball support or ball identity/ID - exactly one filtered position, matching today's "one marker" behavior.
- No re-tuning of `Axis1DKalmanFilter`'s existing `processNoise`/`measurementNoise` defaults for the player-tracking path; they were already chosen for occlusion-bridging prediction, and this change's own new smoothing-focused constants (ball tracker's filter, coast bound) are new placeholders in the same spirit as the codebase's existing untuned thresholds (e.g. `KeypointRefreshChangeThreshold`), not yet validated against real broadcast footage.

## Decisions

**Report the Kalman posterior directly, no second blend layer.** `Axis1DKalmanFilter.Correct` already computes `position + gain * (measurement - position)` - a variance-weighted blend between the prior estimate and the new detection. Adding a second, separate "blend raw detection with predicted box by some alpha" step on top would duplicate what the filter already does, with a second, redundant tuning knob. Instead: expose the corrected estimate directly.
- `Axis1DKalmanFilter` gains a way to read `_position` without calling `Predict()` (e.g. a `Position` property, or have `Correct` return it) - currently the only accessors are `Predict()` (advances state) and `Correct()` (void).
- `BoxMotionPredictor.Correct(box)` changes from `void` to returning the corrected `(Left, Top, Right, Bottom)` box, assembled from the four axes' post-correction values - mirroring what `Predict()` already returns for the predicted box.
- `ByteTrackPlayerTracker.ApplyMatch` sets `track.LastBox = track.Predictor.Correct(box)` instead of `track.Predictor.Correct(box); track.LastBox = box;`. Everything downstream of `LastBox` (rendering, minimap projection, duplicate-IoU suppression) is unchanged - it already treats `LastBox` as "the box to report," it just receives a smoothed value now instead of a raw one.
- Alternative considered: keep reporting the raw box but smooth only the *rendered* position at the overlay layer (e.g. in `MainWindowViewModel` or the Avalonia view). Rejected - that would split "what is this track's position" across two layers (tracker holds the true/raw box, view holds a display-only smoothed copy), and duplicate-track suppression / minimap projection would then need to choose which one to use. Keeping the smoothed value as the one and only reported box keeps a single source of truth.

**New `BallTracker`, not an extension of `ByteTrackPlayerTracker`.** Considered generalizing `ByteTrackPlayerTracker` to a single-object mode instead of writing a new class. Rejected: multi-object association (two-round confidence tiers, color-gated matching, duplicate-track suppression, confirmation-on-spawn) is all irrelevant with at most one object and would just be dead code paths behind flags. A new, much smaller `BallTracker` reusing `BoxMotionPredictor` directly is a better fit, matching how this codebase already keeps `IPlayerTracker`/`ByteTrackPlayerTracker` as the sole implementation of a narrowly-scoped abstraction.
- New `IBallTracker` interface in `src/NBA.Tracking/`, with one implementation `BallTracker`, mirroring `IPlayerTracker`'s `Update`/`PredictOnly`/`Reset` shape:
  - `BallPosition? Update(IReadOnlyList<OnCourtObjectDetection> detections)` - called on detection frames (same cadence `_ballDetector` already runs on). Filters `detections` to `ClassName == "Ball"` internally (so the caller can pass `_lastOtherDetections`/this frame's `Others` unfiltered, same convenience `MainWindowViewModel`'s existing ball-marker LINQ already relies on) and, per the spec's "use only the highest-confidence one," picks the single highest-confidence `Ball` detection among them, if any.
  - `BallPosition? PredictOnly()` - called on frames where no detection attempt ran, advancing the motion model only, exactly like `IPlayerTracker.PredictOnly()`'s existing contract.
  - `void Reset()` - clears filter state, called from the same places `_playerTracker.Reset()` already is (source switch, calibration invalidation) since a new source's ball position has no relationship to the old one.
  - `BallPosition` is a small new record (`Left`, `Top`, `Right`, `Bottom`, `Confidence`) - deliberately not reusing `OnCourtObjectDetection` (which carries a `ClassName` the ball tracker's own consumer already knows) or `TrackedPlayer` (which carries a `TrackId`/`Color` the ball has neither of).
- Internal state: one `BoxMotionPredictor`, a `MissedFrames` counter, and an `IsAcquired` flag (false until the first-ever matched detection). On a miss (`Update` called with no `Ball` detection present), `MissedFrames` increments; while `IsAcquired && MissedFrames <= maxCoastFrames`, `Update`/`PredictOnly` still report the motion-predicted box (advances `Predictor.Predict()` every call, matching `AdvancePredictions`'s per-call-once contract in the player tracker). Once `MissedFrames > maxCoastFrames`, reports `null` and - per the spec's "re-acquire immediately, no confirmation delay" requirement - the *next* matched detection discards the old `BoxMotionPredictor` and constructs a fresh one, so the filter's first `Correct` call initializes directly to the new measurement (per `Axis1DKalmanFilter`'s own documented first-call behavior) instead of blending against a long-stale, high-covariance prior. This is the ball's equivalent of "never revive a terminated track's identity," minus an actual ID.
- Alternative considered: report the ball's raw detection box unmodified once re-acquired within the coast bound (skip smoothing while coasting, only smooth while actively matched). Rejected as unnecessary complexity - `Correct` already handles both cases correctly by construction (a big innovation after several unmatched `Predict()` calls just yields a larger gain-weighted correction, not a discontinuity), so one code path already covers it.

**Ball rendering sources from the tracker, not `_lastOtherDetections`, for the `Ball` class only.** `MainWindowViewModel` gains a `_ballTracker` field (constructor-injected like `_playerTracker`), calls `_ballTracker.Update(...)`/`PredictOnly()` alongside the existing `_playerTracker.Update(...)`/`PredictOnly()` calls (same `isDetectionFrame` gate), and builds the `Ball` raw-view annotation and the minimap `ballMarker` from its returned `BallPosition?` instead of scanning `_lastOtherDetections` for `ClassName == "Ball"`. `_lastOtherDetections` itself is unchanged and keeps including raw `Ball` detections (other non-`Player` classes still read from it as-is; nothing needs a "Ball" case removed from that list, only the two `Ball`-specific rendering call sites are re-pointed).

## Risks / Trade-offs

- [Kalman-smoothed box lags slightly behind a genuinely fast, direction-changing ball/player, trading jitter for a small responsiveness cost] → Same trade-off the existing player-tracking occlusion buffer already accepts (`maxVisibleLostFrames`'s doc comment: "past a couple of misses... it's better to show nothing than a box flying off"); `processNoise`/`measurementNoise` are tunable per-object if the ball (faster, smaller, more erratic than a player) needs a different balance than the player defaults - left as a follow-up tuning pass against real footage, consistent with this codebase's existing convention of documented-but-unvalidated thresholds.
- [A fresh `BoxMotionPredictor` on re-acquisition means the ball's velocity estimate resets to zero right after a coast-bound-exceeded gap, so the very next few frames' smoothing is weaker (behaves like a first-ever detection) until velocity re-establishes] → Accepted: the alternative (keep the stale filter) would drag the reacquired position toward a stale extrapolated trajectory, which is the worse visual artifact of the two per the spec's "re-acquire immediately" requirement.
- [Two independent, uncoordinated Kalman filters (player smoothing, ball smoothing) rather than one shared tuning] → Intentional; a player's and the ball's motion statistics are different enough (size, speed, occlusion pattern) that sharing constants would just recreate the mismatch problem, not solve it.

## Migration Plan

No persisted state or data migration involved - both changes are in-memory per-session tracker behavior. `BoxMotionPredictor.Correct`'s signature change (`void` → box) is source-breaking for its one existing caller (`ByteTrackPlayerTracker.ApplyMatch`), updated in the same change; no other caller exists today.
