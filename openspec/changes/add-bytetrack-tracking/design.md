## Context

Builds directly on `vision/player-detection`'s output shape (`PlayerDetection`: box + `Confidence`, in `src/NBA.Vision`) and reuses the interface + implementation pattern already proven twice (`ICourtKeypointDetector`/`IPlayerDetector`). Unlike those, this capability has no external model file to load, so the usual "null object for missing model" half of that pattern doesn't apply here — see Decisions.

`NBA.Tracking` (`src/NBA.Tracking`) and its future test project are currently empty scaffolds already present in `NBA.slnx`, created ahead of this change. `MainWindowViewModel.OnFrameArrived` already calls `_playerDetector.Detect(...)` once per frame and maps the result straight to unlabeled foot-point `OverlayAnnotation`s (`add-player-detection`); this change inserts the tracker between those two steps and switches the rendered shape from a foot-point to a labeled box, using `OverlayAnnotation.ForBox`, which already exists and already supports a label but has had no caller until now.

## Goals / Non-Goals

**Goals:**
- Give each physical player a stable integer track ID that survives across frames, including brief occlusion or a dip below the high-confidence threshold.
- Implement ByteTrack's core two-round association (high-confidence detections first, then low-confidence detections only against still-unmatched tracks) rather than a SORT-style single-round match that discards low-confidence boxes outright.
- Make the whole association + lifecycle pipeline unit-testable deterministically, frame-by-frame, with hand-constructed detection sequences — no model, no fixture assets, no camera/frame-source dependency.

**Non-Goals:**
- Jersey-number OCR or any multi-frame voting on visual content read from a track's crop — a separate, independent model and a separate change (`design.md`'s Impact section already flags this as a needed follow-on that consumes this change's track IDs).
- Long-term re-identification (recovering a track's *same* ID after it's fully terminated and reappears later, e.g. via an appearance embedding). This change is motion+IoU association only, exactly like the reference ByteTrack algorithm's own scope; a terminated track's ID is never reused or recovered.
- Mapping tracked boxes onto the court-calibration homography (minimap) — out of scope, same boundary `add-player-detection` already drew for raw per-frame boxes.
- Real-time performance tuning against actual broadcast frame rates — flagged as a later concern, not a scope boundary here (same posture `add-player-detection`'s design.md took for running two ONNX models per frame).

## Decisions

**No `Null*` implementation.** Every existing detector-style capability (`ICourtKeypointDetector`, `IPlayerDetector`) needed a null object because its real implementation depends on an external `.onnx` file that might not be present. `IPlayerTracker` has no such dependency — it's a pure algorithm over the `PlayerDetection` lists already in memory. There is exactly one implementation, `ByteTrackPlayerTracker`, always wired, with no conditional file-existence check in `App.axaml.cs`. If it's ever given zero detections it naturally emits zero tracks — no separate degraded path needed.

**Frame-stepped motion prediction, not wall-clock time.** The reference ByteTrack implementation predicts one discrete step per *processed frame*, not per elapsed wall-clock second, and this change follows that: `IPlayerTracker.Update` advances every track's motion model by exactly one step per call, regardless of the real time between calls. This keeps the algorithm deterministic and trivially unit-testable (call `Update` N times, assert on states) without needing to fabricate timestamps or handle variable capture frame rates as a tracking concern. If the capture pipeline's frame rate varies enough in practice to make this a problem, that's a future calibration concern, not a reason to complicate this change's core loop.

**Motion model: four independent 1D (position + velocity) Kalman filters over `cx, cy, w, h`, not one coupled 8-dimensional filter.** The textbook SORT/ByteTrack state vector is a single 8D Kalman filter (`cx, cy, aspect ratio, height` + their velocities, with cross-correlated covariance). That needs general matrix inversion, and no linear-algebra package is currently referenced anywhere in this repo. Decoupling into four independent 2D (`value, velocity`) filters — one each for box center-x, center-y, width, height — needs only closed-form 2x2 math per filter, no matrix library, while still providing genuine predict/update motion smoothing (as opposed to naive last-position-repeated or pure linear extrapolation, which don't shrink prediction uncertainty as observations arrive). The trade-off is losing the cross-axis correlation the coupled filter models (e.g., width and height shrinking together as a player turns sideways aren't modeled as related) — acceptable for keeping short-occlusion position prediction reasonable without a new dependency.

**Association is greedy IoU matching, not the Hungarian algorithm.** The reference ByteTrack implementation solves each round as an optimal bipartite assignment (Hungarian/linear assignment on the IoU cost matrix). This change instead sorts all (track, detection) pairs above the round's IoU threshold by IoU descending and greedily assigns them, skipping any pair where either side is already claimed — the same greedy pattern `OnnxPlayerDetector.SuppressOverlapping` already uses for NMS. Greedy matching can occasionally pick a slightly suboptimal global assignment when many boxes overlap densely, but avoids implementing/depending on a full assignment-problem solver for what is, per-frame, a small N (a handful of players). Revisit only if greedy mismatches are observed to meaningfully hurt ID stability in practice.

**Two confidence tiers are a second, stricter split on top of `IPlayerDetector`'s own threshold**, not a reinterpretation of it. `IPlayerDetector` already only returns detections above its own confidence threshold (spec'd behavior). This change's `highConfidenceThreshold` (constructor parameter, default `0.6`) further splits that already-filtered set into "high" (used for round one, and the only tier allowed to spawn new tracks) and "low" (everything else `IPlayerDetector` returned; used only in round two, only against still-unmatched tracks). Both this threshold and each round's separate IoU threshold (`highConfidenceIouThreshold`, `lowConfidenceIouThreshold`, defaults `0.3`) are constructor parameters, following the existing `confidenceThreshold`/`iouThreshold`-as-constructor-parameter convention from `OnnxCourtKeypointDetector`/`OnnxPlayerDetector`.

**Occlusion buffer is a frame count, not a time span** (`maxLostFrames`, constructor parameter, default `30`), consistent with the frame-stepped motion model decision above. A track survives up to that many consecutive `Update` calls with no matched detection (still being motion-predicted and IoU-matchable each of those calls) before it's terminated and its ID is never reused.

**Track IDs are a monotonically increasing counter scoped to one `ByteTrackPlayerTracker` instance**, starting at 1, never reused after a track terminates — same simple approach `add-player-detection`'s design took wherever an unambiguous simple option existed over a more general one (there, per-model constructor parameters over hardcoding; here, a plain counter over anything needing persistence, since tracks don't need to survive an app restart or a source switch — `MainWindowViewModel.SelectSourceAsync` already resets per-source state like annotations, and will reset the tracker the same way).

## Risks / Trade-offs

- [Greedy IoU matching instead of optimal assignment] → may occasionally swap two players' predicted matches in dense, heavily-overlapping groups; acceptable given small per-frame player counts, revisit only if observed in practice (see Decisions).
- [Decoupled per-axis Kalman filters instead of one coupled 8D filter] → loses cross-axis correlation (e.g. width/height shrinking together); still meaningfully better than no motion model at all for short occlusions, and avoids a new matrix-math dependency.
- [No re-identification after track termination] → a player who leaves frame (or is occluded longer than `maxLostFrames`) and reappears gets a brand-new ID, not their old one. Explicitly out of scope, matching the reference algorithm; a future change could add appearance-embedding-based Re-ID on top without changing this change's output shape (`TrackedPlayer` already carries enough — box + ID + confidence — that a Re-ID layer could sit alongside it).
- [`highConfidenceThreshold`/IoU thresholds/`maxLostFrames` are unvalidated defaults, not empirically tuned] → same posture as every other threshold in this codebase so far (`OnnxPlayerDetector`'s confidence/IoU thresholds, `OnnxCourtKeypointDetector`'s), exposed as constructor parameters specifically so they don't need a code change once real footage is available to tune against.
