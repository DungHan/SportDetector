**Architecture note beyond what 6.1-6.10 anticipated**: making `NBA.App` buildable on this non-Windows machine (needed to verify anything in this group at all) required multi-targeting `NBA.App` itself the same way `NBA.Capture` is multi-targeted (`net10.0;net10.0-windows10.0.19041.0`), with `Services/CapturePlatform.{Windows,Fallback}.cs` selecting the real `WindowsGraphicsCaptureFrameSource`/`WindowsCaptureSourceEnumerator` on Windows and `FakeFrameSource`/`FakeCaptureSourceEnumerator` (from `NBA.Capture`'s `Testing` namespace) elsewhere. This wasn't spelled out in design.md but follows directly from its stated Non-Goal ("Avalonia is chosen for the UI specifically so the rest of the app isn't blocked on [Windows-only capture] later") - flagging it here rather than silently expanding scope.

**Avalonia.Headless setup note**: `NBA.App.Tests` had to become an **xunit v3** project (`OutputType=Exe`, `xunit.v3` package pinned to **3.2.2** specifically, `TestingPlatformDotnetTestSupport=true`) because `Avalonia.Headless.XUnit` 12.1.2 depends on `xunit.v3.extensibility.core`; the newer `xunit.v3` 4.0.1 line changed a method signature Avalonia's test discoverer binds to, causing a `MissingMethodException` at discovery time - pinning to 3.2.2 fixed it. `dotnet test` itself fails on this SDK with a VSTest-deprecation error even with the MTP opt-in property set; the working invocation on this machine is building normally and then running the produced executable directly with `DOTNET_ROOT` set, e.g.:
```bash
DOTNET_ROOT="$HOME/.dotnet" ./tests/NBA.App.Tests/bin/Debug/net10.0/NBA.App.Tests
```
This is worth revisiting on a real Windows dev box, where `dotnet test`/IDE test explorers may behave differently.
