## Context

See proposal.md for motivation. Relevant current state:

- `OnnxPlayerDetector` (`src/NBA.Vision/OnnxPlayerDetector.cs`) wraps one `OnnxModelPipeline<TInput, TOutput>` (`src/NBA.Inference/OnnxModelPipeline.cs`) instance. `OnnxModelPipeline.Run(...)` calls `_session.Run(...)` exactly once and hands the raw output tensor to a single `postprocess` delegate producing one `TOutput` - there is no built-in caching or multi-consumer story; whatever `TOutput` the postprocess delegate returns is the *only* thing a `Run(...)` call produces. Today that delegate reads one class channel (`playerChannel = 4 + playerClassId`) and returns `IReadOnlyList<PlayerDetection>`.
- `MainWindowViewModel.ProcessFrameArrived` (`src/NBA.App/ViewModels/MainWindowViewModel.cs:218-239`) calls `_playerDetector.Detect(...)` once per detection frame, feeds the result straight into `_playerTracker.Update(...)`, and builds `playerAnnotations` from the tracker's output (not from the raw detections) - `IPlayerDetector`'s only consumer in the app today is this one call site.
- Scoreboard OCR (`MainWindowViewModel.cs:293-320`) runs on its own ~1Hz wall-clock throttle, decoupled from the detection-frame cadence - it can fire on a frame where no detection was attempted at all. It reads `_profileStore.Load(sourceKey)?.ScoreboardRegion ?? NormalizedRect.DefaultScoreboardRegion` for the crop rectangle every time it fires.
- `RawOverlayView.axaml.cs`'s `CreateControls(AnnotationVisual)` (`src/NBA.App/Views/RawOverlayView.axaml.cs:71-135`) draws every non-keypoint box the same fixed color (`#FF4040`); `StyleKey` is only inspected to special-case keypoints today.
- `tests/NBA.App.Tests` has a `StubPlayerDetector` (implementing `IPlayerDetector`) used to drive `MainWindowViewModelTests` without a real model.

## Goals / Non-Goals

**Goals:**
- One inference pass per detection frame produces detections for all 9 classes - never a second `_session.Run(...)` call to get the non-`Player` classes.
- `PlayerDetection`'s shape and `tracking/player-tracking`'s consumption of it are provably unchanged (existing `ByteTrackPlayerTracker`/team-color-gating tests keep passing unmodified).
- Non-`Player` classes become visible (overlay boxes) and useful (scoreboard OCR crop-region source) with minimal new plumbing, reusing the existing generic `OverlayAnnotation`/`RawOverlayView` mechanism.

**Non-Goals:**
- Per-class confidence/IoU threshold tuning - one shared `confidenceThreshold`/`iouThreshold` (same convention as today) applies across all 9 classes; revisit only if real footage shows a specific class needs its own threshold.
- Tracking, re-identification, or any per-track state for non-`Player` classes (e.g. no "ball tracking") - these are per-frame detections only, same posture `vision/player-detection` itself had before tracking was added on top of it in a separate change.
- Per-class OCR (cropping/recognizing `Period`, `Shot Clock`, `Team Points`, etc. as separate regions and merging results) - see proposal.md's Decisions; this change only changes where the *one* existing crop rectangle comes from.
- Any change to `IScoreboardOcrEngine`, `FrameCropper`, or `ScoreboardTextParser`'s internals.

## Decisions

**A new `IMultiClassObjectDetector` interface (single `Detect(...) -> MultiClassDetectionResult` method) supersedes `IPlayerDetector` at the `MainWindowViewModel` wiring layer; `IPlayerDetector`/`PlayerDetection`/`NullPlayerDetector` are unchanged and keep existing.** This is the only way to guarantee one inference pass serves both consumers: if `MainWindowViewModel` called two separate interface methods (one for players, one for everything else) each backed by its own `_pipeline.Run(...)`, inference would run twice per frame - the exact cost this change exists to avoid. Instead, `MultiClassDetectionResult(IReadOnlyList<PlayerDetection> Players, IReadOnlyList<OnCourtObjectDetection> Others)` bundles both outputs of one `Run(...)` call; `MainWindowViewModel` calls this once per detection frame, passes `.Players` to `_playerTracker.Update(...)` exactly as it passes `_playerDetector.Detect(...)`'s result today (byte-for-byte identical downstream behavior), and uses `.Others` for the two new consumers below. `IPlayerDetector` remains a real, valid interface (any future non-multiclass detector could still implement it), just no longer what `MainWindowViewModel` depends on for its detection call site.

**`OnnxPlayerDetector` is renamed `OnnxMultiClassObjectDetector`** (implementing `IMultiClassObjectDetector`, not `IPlayerDetector`) since decoding every class is now its whole job, not a player-specific detector that happens to ignore other channels. A `NullMultiClassObjectDetector` (always returns `Players: []`, `Others: []`) replaces `NullPlayerDetector` at the `App.axaml.cs` wiring layer, mirroring the existing missing-model degraded-path convention exactly (`File.Exists(playerDetectionModelPath) ? new OnnxMultiClassObjectDetector(...) : new NullMultiClassObjectDetector()`).

**Postprocessing loops over every class channel, running independent per-class NMS, instead of reading one hardcoded channel.** For each of the 9 channels: collect every candidate above `confidenceThreshold` on that channel, run the existing `SuppressOverlapping` NMS logic within that channel's own candidates only (per `vision/on-court-object-detection`'s "one class's boxes never suppress another class's boxes" requirement), then route the surviving boxes to either `PlayerDetection` (for the configured `playerClassId` channel, including today's upper-body color sampling - unchanged) or `OnCourtObjectDetection` (every other channel, no color sampling - only `vision/player-detection`'s team-color-gating needs it). This is a straightforward generalization of the existing single-channel loop, not a new algorithm.

**`OnCourtObjectDetection` carries a class *name* (`string ClassName`), not a raw class index**, resolved via a `classNames: IReadOnlyList<string>` constructor parameter supplied by the caller (`App.axaml.cs`) from the model's own embedded metadata (`models/README.md`'s verified `{0: 'Ball', 1: 'Hoop', ...}` list) - same "caller supplies the verified index/list, never hardcoded/guessed" posture `add-team-color-track-gating` already established for `playerClassId`. Downstream consumers (overlay labels, the scoreboard-class filter below) match by name (`"Period"`, `"Shot Clock"`, ...), which is self-documenting and doesn't break if channel ordering ever changes in a future model re-export as long as the supplied `classNames` list is updated to match.

**Non-`Player` overlay boxes get one fixed color per class, via a small `ClassName -> Brush` lookup added in `RawOverlayView.axaml.cs`, not a fully generic style system.** `CreateControls` already special-cases `StyleKey == "keypoint"`; this adds one more lookup (class name as `StyleKey`) alongside it, falling back to the existing fixed red for anything unrecognized (including tracked-player boxes, whose `StyleKey` stays unset, preserving today's look exactly). A small fixed palette (e.g. one color per class, chosen for visual distinctness) is simplest and sufficient - no need for a configurable/themeable color system for a debug/visibility overlay.

**Scoreboard OCR's crop-region precedence becomes: manual `SourceProfile.ScoreboardRegion` override (if set) > most recent detected scoreboard-object union box (if any) > `NormalizedRect.DefaultScoreboardRegion`.** The manual override exists specifically so a user can correct a source where automatic placement is wrong; it must keep winning outright, unchanged, or a manual fix would silently stop working the moment detection also produces boxes. The detected union box only fills the gap the hardcoded bottom-15%-of-frame default previously filled - a strict improvement (a real, source-specific measured region) with the same fallback posture as before when it's unavailable.

**The detected union box is cached from the most recent detection frame, not recomputed at OCR's own 1Hz cadence.** OCR runs independently of the detection-frame cadence (per Context above) and must not trigger its own detection pass. `MainWindowViewModel` keeps a per-source `_lastScoreboardObjectRegion: NormalizedRect?` field, overwritten on every detection frame from that frame's `.Others` filtered to the five scoreboard-related class names (`Period`, `Shot Clock`, `Team Name`, `Team Points`, `Time Remaining`) and converted to a normalized union rect (or left unset if none of those classes were detected that frame - the previous cached value, if any, keeps being used until a frame actually updates it). Reset to `null` on source switch, mirroring how other per-source detection state (e.g. `_lastKeypoints`, the tracker) is already reset there. No explicit staleness expiry - see Risks.

**Union box is computed over image-pixel coordinates, then normalized against the same reference frame `NormalizedRect.DefaultScoreboardRegion`/`SourceProfile.ScoreboardRegion` are already normalized against** (the playback-region crop once known, else the full captured frame - see `MainWindowViewModel.cs:304-311`'s existing comment on this), so it plugs into the exact same `FrameCropper.Crop(...)` call already there without changing that call's shape.

## Risks / Trade-offs

- [A class never detected for a given source (e.g. an unfamiliar broadcast graphic style) leaves `_lastScoreboardObjectRegion` permanently `null`] → falls back to `NormalizedRect.DefaultScoreboardRegion` every time, identical to today's behavior for every source - no regression, just no improvement for that source.
- [No staleness expiry on the cached detected region] → if the scoreboard genuinely moves within a broadcast (unusual, but e.g. a graphics-package change mid-game) and detection briefly misses it, OCR keeps using the last good region for a beat rather than immediately falling back; acceptable since the next successful detection frame overwrites it, and a slightly-stale-but-recent real region is still better than the crude fixed default.
- [Renaming `OnnxPlayerDetector`/replacing `IPlayerDetector` at the wiring layer is a breaking change to `MainWindowViewModel`'s constructor signature] → `tests/NBA.App.Tests`' `StubPlayerDetector` and any test wiring against it need updating to the new `IMultiClassObjectDetector` shape; `IPlayerDetector`/`PlayerDetection` themselves are unaffected, so this is scoped to the app-wiring layer only, not a spec-level break.
- [One shared confidence/IoU threshold across 9 classes instead of per-class tuning] → a class whose real-footage confidence distribution differs a lot from `Player`'s (e.g. small on-screen elements like `Shot Clock` digits) may under- or over-detect at the shared default; acceptable for a first version, same "tune later against real footage" posture as every other threshold in this codebase.
